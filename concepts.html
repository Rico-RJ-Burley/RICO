Key Concepts

Ten ideas that explain how web servers do their job. When you’ve read them, test yourself with the quiz.

1. The Client-Server Model

The web is built on two roles. The client (your browser) asks for something, and the server answers. The server waits for requests and can answer thousands of clients at once. The client never talks to the server’s files directly; it only gets what the server chooses to send.

2. HTTP and HTTPS

HTTP is the set of rules for how requests and responses are written. Each request has a method (like GET or POST), a path (like /about.html), and headers with extra details. HTTPS is HTTP sent through an encrypted TLS connection, so nobody in between can read or change it. HTTP uses port 80 and HTTPS uses port 443.

3. DNS (Domain Name System)

Computers find each other with numeric IP addresses, but people remember names. DNS is the internet’s phone book: it turns a name like github.io into the IP address of the server that hosts it. Without DNS, you would have to type numbers to visit any website.

4. HTTP Status Codes

Every response starts with a three-digit code that tells the browser how the request went.

Common status codes
CodeMeaning
200OK: everything worked
301Moved permanently to a new address
403Forbidden: you are not allowed to see this
404Not found: the page doesn’t exist
500Internal server error
503Service unavailable: the server is too busy or down

5. Static vs. Dynamic Content

Static content is a file sent exactly as it is stored, so every visitor sees the same thing. Dynamic content is built by code each time someone asks, often using a database, so the page can change for each user, such as a shopping cart or a social media feed. Many sites mix both: the web server sends static files itself and hands dynamic requests to an application server.

6. Reverse Proxy

A reverse proxy is a server that sits in front of other servers and receives every request first. It then passes each request to the right server behind it. This hides the inner servers from the internet, lets one place handle HTTPS, and makes it easy to add caching or security rules. Nginx is often used this way.

7. Load Balancing and Caching

These are the two main ways to handle lots of visitors. Load balancing spreads requests across several servers so no single one gets overwhelmed, and keeps the site up if one server fails. Caching saves copies of popular responses in fast memory or on a CDN so they can be sent again without redoing the work.

8. Ports

One server can run many programs at once, so an IP address alone isn’t enough to deliver a request. A port number tells the server which program should get the traffic, the way an apartment number finishes a street address. A web server listens on port 80 for HTTP and port 443 for HTTPS. Browsers fill these in automatically, which is why you never type them, but you will see other ports during development, such as http://localhost:8080.

9. TLS Certificates

Encryption only helps if you are talking to the right server. A TLS certificate is a digital ID card, issued by a trusted certificate authority, that proves a server really controls its domain name. When you open an HTTPS site, the browser and server run a short TLS handshake: the server presents its certificate, the browser checks it, and the two agree on secret keys to encrypt everything after that. If the certificate is expired or for the wrong name, the browser shows a warning page.

Free certificates: Let’s Encrypt hands out certificates at no cost. They expire after a few months, so servers use tools that renew them automatically.

10. Virtual Hosting

A single web server can host hundreds of different websites. This is called virtual hosting. Every HTTP request includes a Host header naming the site the browser wants, and the server uses it to pick the right folder of files. Apache sets this up with <VirtualHost> blocks and Nginx with server blocks. Shared hosting plans and GitHub Pages both work this way, which keeps hosting cheap.
